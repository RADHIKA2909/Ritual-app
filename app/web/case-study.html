Case Study · Product & Engineering

Habits don't fail from a lack of willpower.
They fail because no one's watching.

Ritual is a group habit tracker I built end to end: the weakest-link streak algorithm, the real-time backend, a rough deployment, and a demo account that keeps itself three months old.

The problem

Most habit trackers are built around one person's willpower. Miss a day alone and there's no real cost to missing it again tomorrow, so the streak quietly dies and the app turns into another abandoned icon.

I wanted Ritual to work differently: habits hold up better when someone else is watching. Not a leaderboard full of strangers, just a small group of people who'd actually notice if you disappeared.

The product

Rituals belong to a group, not to you.

Every habit in Ritual, a "ritual," is owned by a group, never a single person. A group might be two people holding each other to a gym routine, a five-person friend circle, or just one person who still wants the same streaks and heatmaps for themselves. Checking in, reacting to a groupmate's check-in, watching a shared streak survive the week: it all happens in real time, so the app feels more like a group chat than a private to-do list.

Key decisions

A few decisions that shaped everything else

ALGORITHM

The weakest-link streak

A group's weekly streak isn't an average, and it isn't just the best member's count. It's the minimum completion rate across every current member, checked against the ritual's weekly minimum, on Monday-anchored UTC weeks. If four people hit their target and one didn't, the group's streak reads exactly like that one person's week did. That's strict on purpose: a streak that flatters the group's best performer doesn't actually hold anyone accountable, since it lets someone quietly check out without it ever showing up in the number that matters.

Status per ritual (on_track / needs_attention / at_risk / complete) comes from pace against that minimum, not a raw count. So a group sitting at 1 of 3 check-ins on a Monday correctly reads as fine, and that same 1-of-3 on a Friday reads as at risk.

ARCHITECTURE

The server is the only source of truth

Every streak, status badge, and health score gets computed once, on the server, straight from the raw check-in documents. The Flutter client never recomputes any of it. That sounds like a small rule, but it matters: the UI can't drift from the backend's idea of "on track" if it was never allowed to have its own idea in the first place. Its job is just to render what the server already decided.

PRODUCT

"My progress" became "our progress"

Going back through the UI, I noticed it was quietly talking to the individual everywhere: "your streak," a lone completion ring, a "Go" button that gave no sense of who else was waiting. So I rewrote that language across the app. The home screen now leads with the group's status, not yours. "Check in" replaced the vague "Go." Every card separates your check-in from the group's completion, instead of blurring the two into one green checkmark.

Engineering challenges

What actually went wrong

01

The mobile app that had to stop being one

Ritual started as a Flutter app targeting mobile and web at once. Once it was clear the people who mattered were opening a link, not installing an app, I pulled out every mobile-only code path: platform channels, mobile-specific navigation, permissions nothing used. What was left was one deliberately web-only app instead of a compromise between two.

02

A deployment that took three tries

Shipping the backend to Render turned into a chain of failures, each one hiding the next behind it. The build kept exiting with no useful log, until the real one showed up: NODE_ENV=production was quietly telling npm install to skip devDependencies, including TypeScript itself, before tsc ever got to run. Once that was fixed, the next failure was a crash loop against 127.0.0.1:27017, a hardcoded local-Mongo fallback still sitting in the config, standing in for a real MongoDB Atlas connection string that had never actually been set.

A node_modules folder had also ended up committed to git somewhere along the way, carrying macOS-only native binaries onto a Linux build server. Caught and removed before it could cause a fourth failure.
03

A demo account that never goes stale

The live app needed a way for an interviewer to see three months of real usage without anyone actually using it for three months. My answer was a demo account that regenerates its own history (three groups, realistic check-in patterns, chat) once per calendar day, so the trailing window is always "the last 90 days" relative to whenever someone opens the link, instead of a frozen date range that slowly goes stale.

Since it runs against the same production database as real users, the regeneration only ever touches an ID list it derives fresh on every call, never a blanket delete. A single atomic findOneAndUpdate claim makes sure two visitors logging in at the same moment can't trigger the rebuild twice. Write-guards stop the shared account from creating or joining real groups, and a rate cap limits what a public, unmoderated chat thread can do.

Outcome

What's live today

Ritual runs end to end on free-tier infrastructure: Flutter web on Firebase Hosting, an Express and TypeScript API on Render, MongoDB Atlas for the database, real-time sync over Socket.IO. The demo account lets anyone see it exactly as it would look after months of real use.
